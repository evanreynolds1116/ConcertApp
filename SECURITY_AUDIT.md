**Scope:** the whole repo at commit `a6f607d`, plus its git history:
- the web app
- the Supabase migrations, storage and auth config

## Step 1: How the app works

**What it does:**
- **Purpose:** log US concerts you went to, see stats, and follow friends.
- **Stack:**
  - a pnpm and Turborepo monorepo
  - a Next.js 16 web app (App Router, server actions)
  - Supabase: Postgres with RLS, Auth, Storage and one Deno Edge Function
  - the setlist.fm REST API for concert data
- **Run:** locally only so far, with Docker running the Supabase CLI stack and `next dev`. Deploying to hosted Supabase and Vercel is Phase 6 and not done yet.

**Entry points that take outside input:**

| Entry point | Who can reach it | Where |
| --- | --- | --- |
| Next.js pages | Signed-in users. The middleware redirects others, and the `(app)` layout calls `requireViewer()` | `apps/web/src/app/(app)/**`, `apps/web/src/proxy.ts` |
| Sign-in and sign-up forms (server actions), plus the `?next=` query parameter | Anyone | `apps/web/src/app/(auth)/actions.ts`, `sign-in/page.tsx` |
| Server actions: save, edit and delete a concert; follows; privacy; profile; avatar; delete account; feed and log paging | Signed-in users | `apps/web/src/app/(app)/**/actions.ts`, `social-actions.ts`, `log-actions.ts` |
| `GET /auth/reset-session` route handler | Anyone | `apps/web/src/app/auth/reset-session/route.ts` |
| Supabase's own API (database tables, function calls, auth, storage), called with the publishable key. This bypasses the Next.js server entirely, so the database rules are the real security boundary. | Anyone with the public key. Data needs a signed-in token. | Migrations in `supabase/migrations/` |
| `setlist-search` Edge Function (POST, JSON) | Signed-in users (token checked in code) | `supabase/functions/setlist-search/index.ts` |
| Avatar uploads, straight from the browser to Storage | Signed-in users, own folder only | `settings/profile-settings.tsx`, storage policies in `20261001050805_social.sql` |
| Env vars: Supabase URL and publishable key (web); `SETLISTFM_API_KEY` (function); scripts' `.env` | Deploy-time configuration | `.env.example` files |
| CLI scripts (`scripts/*.ts`, command-line arguments) | Developer only, never deployed | `scripts/` |

There are no webhooks, message queues or admin endpoints.

**Data and third parties:**
- **Supabase Postgres:**
  - profiles
  - shared artists, venues and shows
  - concert logs and lineups
  - follows and activity
- **Supabase Auth:** emails and password hashes, in Supabase's own schema.
- **Supabase Storage:** the private `avatars` bucket.
- **Outbound calls:** only `https://api.setlist.fm`, from the Edge Function and the local scripts.

**Users and what they may do:**
- **Signed-out visitors:**
  - sign up and sign in
  - check whether a username is free (`is_username_available`)
  - nothing else; no tables are granted to them
- **Signed-in users:**
  - read every profile's name and avatar
  - read logs, lineups, stats and activity of users where `can_view` is true: themselves, public accounts, or private accounts they follow
  - write only their own logs, lineups, profile, follows and avatar files
  - accept or decline requests made to them
- **Admins:** none. There's no admin role and there are no admin features.

## Step 2: Findings

### M1 · Medium: anyone can set the names of shared venues, artists and festival days

**Where:**
- `supabase/migrations/20261001152723_headliner_setlist_links.sql:79-119` (`log_concert`: venues and shows)
- `supabase/migrations/20261001012609_log_browse_and_edit.sql:34-47` (`private.resolve_artist`)

**What's wrong:** venues, artists and shows are shared rows. `log_concert` runs with elevated rights because clients can't write those tables directly. It trusts what the caller sends for setlist.fm-sourced logs:
- **Venues:** `p_venue.setlistfmId`, `name`, `city` and `state`. The first log for a setlist.fm venue ID creates the venue with the caller's name, and later logs reuse it (`on conflict (setlistfm_venue_id) do update set setlistfm_venue_id = …` never renames).
- **Artists:** each artist's `mbid` and `name`. The first log for an MBID creates the artist with the caller's name. A setlist.fm-sourced call can also attach any MBID to an existing manual artist with the same name (`update public.artists set mbid = …`).
- **Shows:** `p_festival_name`, `p_festival_day_label` and `p_setlistfm_url`. The first writer wins (`coalesce(public.shows.festival_name, excluded.festival_name)`), and that includes manual logs. A manual venue gets adopted by the first setlist.fm log that matches its name, city and state, and the show inherits the manual user's festival name.

**How an attacker would use it:** sign up, then call `log_concert` directly through the Supabase API, skipping the app, with real setlist.fm IDs and made-up names. For example, the MBIDs of popular artists and the venue IDs of big arenas, with offensive or misleading names.
- Every later user who logs those artists or venues sees the attacker's names in their log, concert pages, stats and leaderboards.
- Artist names are shown to every user who logs them, including on profiles and the public feed.
- Deleting the attacker's own logs doesn't remove the shared rows, and there's no admin tool to fix them.
- Wrong MBIDs also split one artist into two, which skews stats.

React escapes everything, so this can't run scripts. It's a content and data-integrity attack, not code execution.

**Fix (pick one):**
1. **Sign what the server returns (recommended).** Have the Edge Function sign each lineup result: a keyed hash (HMAC) over venue ID, name, city, state, date, festival name and day label, and each artist's `(mbid, name)`. Keep the signing key in Supabase Vault. `log_concert` checks the signature for `source = 'setlistfm'` and refuses unsigned or altered input. Manual logs keep working, since they never carry setlist.fm IDs.
2. **Look it up on the server.** Make `log_concert` callable only by the server: revoke it from `authenticated` and call it from a server action using the secret key, with the server action re-fetching the chosen show from setlist.fm first. This puts a secret key in the web server, which is a bigger change.
3. **At minimum, stop inheriting from manual logs.** Don't let manual logs fill in a show's festival name or day label for setlist.fm logs: store the festival label on the log, or let verified setlist.fm data overwrite manual data. Add a small admin script to rename or merge bad shared rows.

**Confidence:** high. The code path is direct, and the function is granted to every signed-in user.

### M2 · Medium: the sign-in `next` redirect can be bypassed with a tab or newline character

**Where:**
- `apps/web/src/lib/redirect.ts:2-12` (`safeNextPath`)
- used at `apps/web/src/app/(auth)/actions.ts:67`
- the value comes from `?next=` through `sign-in/page.tsx:8` and `sign-in-form.tsx:12` (a hidden input)

**What's wrong:** `safeNextPath` accepts any string that starts with `/` but not with `//` or `/\`. Browsers' URL parsing removes tab and newline characters, so `"/\t/evil.com"` passes the check and resolves to `https://evil.com/`. I confirmed that resolution with Node's WHATWG URL parser, which matches browsers.

**How an attacker would use it:** send a phishing link like `https://musicjunkie.app/sign-in?next=/%09/evil.com`. Next.js decodes `%09` into a real tab before it reaches the hidden input. The victim signs in on the real site and is then sent to `evil.com`, which can show a fake "session expired, sign in again" page to collect their password.

**Fix:** reject control characters and compare origins:

```ts
const url = new URL(next, "http://x"); // resolve like a browser would
if (/[\u0000-\u001f\\]/.test(next) || url.origin !== "http://x") return "/";
return url.pathname + url.search + url.hash;
```

Add unit tests for `/\t/x`, `/\n/x`, `//x`, `/\x`, `https://x` and `/ok?a=1`.

**Confidence:** medium-high. The check is bypassable for certain. I didn't run it end to end, so I haven't confirmed that Next.js's handling of a server-action redirect passes the tab through to the browser. To verify: run the app, then post the sign-in form with `next` set to `"/\t/example.com"`.

### M3 · Medium: no rate limit on `setlist-search`, which shares one setlist.fm key

**Where:**
- `supabase/functions/setlist-search/index.ts:34-60`
- request budgets at `supabase/functions/_shared/setlistfm/search.ts:26-33`

**What's wrong:** any signed-in user can call the function as often as they like. Sign-up is open to anyone. One festival search makes up to 20 setlist.fm requests, and a lineup up to 10 per venue, with up to 10 venues. Requests are spaced 600 ms apart through one queue per worker.

**How an attacker would use it:** sign up, then loop festival searches with different years.
- **Burns the key:** setlist.fm's rate limit and daily quota are shared by every user. setlist.fm can throttle or revoke the key under its terms ("unreasonable or disproportionately large load").
- **Starves other users:** the queue is shared per worker, so one user's 12-second searches hold up everyone else's.

**Fix:**
- Add a per-user limit in the function, such as N searches per minute per user ID. Use a small Postgres table or Supabase's rate-limiting pattern, and return 429 when it's exceeded.
- Also cap the number of searches in flight per user.
- Optionally add a total daily budget, with an alert.

**Confidence:** high that the limit is missing. How much damage it does depends on setlist.fm's quotas.

### M4 · Medium: no security headers

**Where:** `apps/web/next.config.ts:3` (an empty config). There's no `headers()` and no Content-Security-Policy middleware.

**What's wrong:** responses have no Content-Security-Policy, `frame-ancestors` or `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy` or `Permissions-Policy`. HSTS depends on the host. Vercel adds it for `*.vercel.app`, but check it for a custom domain. Next.js also sends `X-Powered-By: Next.js`.

**How an attacker would use it:**
- **Clickjacking:** frame the app on another site and trick a signed-in user into clicking Follow, Accept or Delete concert.
- **No backstop for XSS:** if a cross-site scripting bug ever appears, there's no CSP to limit it. That matters more here because session cookies are readable by JavaScript (L4).

**Fix:** add an `async headers()` block in `next.config.ts` for all routes:
- `Content-Security-Policy`, with `default-src 'self'`:
  - `connect-src` allows the Supabase URL
  - `img-src` allows `'self'`, `data:`, `blob:` and the Supabase Storage origin
  - `frame-ancestors 'none'`
  - `script-src 'self'`, with a nonce if inline scripts need one
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy: camera=(), microphone=(), geolocation=()`
- `Strict-Transport-Security: max-age=63072000; includeSubDomains`
- `poweredByHeader: false`

**Confidence:** high.

### M5 · Medium: sign-in goes through the Next.js server, which weakens Supabase's per-IP rate limit

**Where:**
- `apps/web/src/app/(auth)/actions.ts:56-67` (`signInWithPassword` and `signUp` run on the server)
- the local limits are in `supabase/config.toml:196-208` (`sign_in_sign_ups = 30` per 5 minutes per IP)

**What's wrong:** Supabase Auth limits sign-ins per client IP. Here the client is the Next.js server, so every user's sign-ins appear to come from the server's few IPs (Vercel's). Two problems follow:
- **Easy lockout:** one attacker sending about 30 bad sign-ins every 5 minutes through the form could use up the shared limit, so real users can't sign in.
- **Weak brute-force protection:** per-attacker throttling disappears. Attackers can also call Supabase Auth directly, where it limits per IP. There's no CAPTCHA and no per-account lockout.

**Fix:**
- Either sign in from the browser with the Supabase client, so Auth sees the real client IP, or forward the client IP and configure Auth to trust it. Check the hosted Supabase options for this.
- Turn on Supabase's CAPTCHA (Turnstile or hCaptcha) for sign-up and sign-in.
- Optionally rate-limit the server action per IP and per email.

**Confidence:** medium. This depends on how hosted Supabase counts the IP for server-side calls, which I couldn't verify locally.

### L2 · Low: `can_view` can be called with any viewer, revealing private follow links

**Where:** `supabase/migrations/20260930235925_privacy_and_triggers.sql:42-59`. It's `security definer` and granted to `authenticated`.

**What's wrong:** any signed-in user can call `select can_view('<X>', '<Y>')` with any two user IDs. User IDs are visible on profiles. If Y is private and the result is true, X follows Y. For two private users, the RLS policies would otherwise hide that.

**Fix:** inside `can_view`, return false unless `viewer_id = auth.uid()` (and drop the parameter if nothing else needs it). Alternatively, move it to the `private` schema behind a wrapper that takes no viewer parameter. Add a pgTAP test for this.

**Confidence:** high. Impact is low: it reveals only who follows whom.

### L3 · Low: shows and venues entered only by private users are visible to every signed-in user

**Where:** `20260930235925_privacy_and_triggers.sql:97-103` (artists, venues and shows are readable by every signed-in user).

**What's wrong:** a manual entry creates shared rows. If a private user logs a one-off show, for example a house show at a venue they name after a friend's address, that venue and show, with its festival name, can be read by anyone. Who attended stays hidden. This is by design ("Nothing here says who attended what"), but rare manual entries can still identify someone.

**Fix (optional):** limit the shows, venues and artists anyone can see to ones with at least one log they're allowed to see. Or keep manual venues private to their creator until someone else logs the same show. Alternatively, document the trade-off.

**Confidence:** high. Impact is low.

### L4 · Low: session cookies are readable by JavaScript

**Where:** `apps/web/src/lib/supabase/server.ts` and `client.ts`, which use `@supabase/ssr` 0.12.7 defaults (`httpOnly: false`, `sameSite: "lax"`, and no explicit `secure`).

**What's wrong:** the access and refresh tokens are in cookies that browser JavaScript can read. Any future cross-site scripting bug would let an attacker steal a refresh token and take over the session for a long time. I found no XSS sinks today (see "Checked and clean"), so this is a hardening point.

**Fix:**
- Add a strict CSP (M4).
- Set `cookieOptions: { secure: true }` in production.
- If the browser client isn't needed for the data, consider server-only auth with `httpOnly` cookies. The avatar upload uses the browser client, so it would need to move to a server action or a signed upload URL.

**Confidence:** high that the cookies are readable by script. Real-world risk is low.

### L5 · Low: any site can sign you out

**Where:** `apps/web/src/app/auth/reset-session/route.ts:11-14`

**What's wrong:** a GET request signs the user out. Any site can include `<img src="https://musicjunkie.app/auth/reset-session">` to log visitors out. It's a nuisance only.

**Fix:** make it POST-only with a same-origin check. Or only clear the session when there's no profile, which is what it's meant for.

### L6 · Low: deleting an account needs no password, and calling `delete_account()` directly leaves avatar files behind

**Where:**
- `apps/web/src/app/(app)/settings/actions.ts:96-110`
- `supabase/migrations/20261001050805_social.sql:257-271`

**What's wrong:**
- **No re-authentication:** anyone with a valid session can permanently delete the account, for example on a shared computer or with a stolen token. Typing the username isn't a password.
- **Orphaned avatars:** `delete_account()` can be called directly, skipping the server action's file cleanup. The avatar files then stay readable to signed-in users.

**Fix:**
- Require the current password, or a recent sign-in, before deleting.
- Move the avatar cleanup into the database, for example a trigger on `auth.users` delete or a scheduled cleanup job, so every path removes the files.

**Confidence:** high. Impact is low.

### L9 · Low: avatar uploads trust the declared file type, and anyone signed in can list all avatars

**Where:** `supabase/migrations/20261001050805_social.sql:12-18`

**What's wrong:**
- **File type:** `allowed_mime_types` checks the content type the uploader declares, not the file's actual contents. Someone calling the Storage API directly could upload any bytes up to 1 MB labeled `image/png`. Storage serves them with that declared type, from Supabase's domain, not the app's. That limits the harm, but they're still unchecked files.
- **Listing:** the read policy lets any signed-in user list every avatar folder, which reveals every user ID that has an avatar.

**Fix:**
- Re-encode uploads on the server, or check the file's leading bytes in an upload hook or Edge Function.
- Narrow the read policy so users can fetch avatar files but not list folders. For example, serve avatars only through server-made signed URLs, as the app already does, and drop the broad read policy.

**Confidence:** medium. I couldn't check Storage's actual response headers for a mislabeled file without the hosted service.

### L10 · Low: weak password policy

**Where:** `supabase/config.toml:181-184` (`minimum_password_length = 8`, `password_requirements = ""`) and the matching Zod schema.

**What's wrong:** 8-character passwords with no other rules are easier to guess, especially combined with M5.

**Fix:** require at least 10–12 characters. Enable leaked-password protection in the hosted project (Have I Been Pwned check). Turn on `secure_password_change` when a password-change flow is added.

  - the middleware and pages verify them with `auth.getClaims()`, which checks the signature
  - so does the Edge Function, which doesn't rely on `verify_jwt`
  - tokens expire after 1 hour, and refresh tokens are rotated
  - the "none" algorithm isn't accepted

**Authorization:** every server action:
- requires a signed-in user (`requireViewer`)
- uses the user's own Supabase client, so RLS applies
- never uses a secret or service key

The database itself checks every write path:
- **Logs and lineups:**
  - `concert_logs` and `log_artists` writes are owner-only through RLS
  - only rating, notes and price can be edited, so a user can't change a log's `user_id`, `show_id` or `source`
  - `update_log` checks ownership
- **Profiles:**
  - only username, display name, avatar and privacy can be edited
  - the avatar path must be in the user's own folder (a check constraint, plus a check in `setAvatar`)
- **Follows:**
  - `follows.status` is set by a trigger, so a follower can't make a follow to a private user "accepted"
  - only the person being followed can accept a request
  - either side can delete
- **Activity:** `activities` can't be written by clients at all.
- **Functions:**
  - every function in `public` revokes execute from PUBLIC
  - a guard test in `03_writes_and_constraints` fails if one doesn't
  - signed-out visitors can only call `is_username_available`
- **Elevated functions:** `log_concert`, `update_log`, `can_view`, `delete_account` and `is_username_available` use `search_path = ''` and act only on `auth.uid()`. M1 and L2 are the exceptions noted above.
- **Tests:** RLS is covered by 236 pgTAP assertions and 23 API smoke tests. Deliberately broken versions of `can_view` and `user_stats` make them fail.

**Admins:** there are no admin features, so there are no admin checks to bypass.

**Injection:**
- **SQL:** no dynamic SQL (`EXECUTE` or `format()`) in any migration. Text search uses `strpos`, so `%` and `_` are literal. The app calls PostgREST through supabase-js, which encodes parameters.
- **Commands:** no shell, `exec`, `eval` or `Function` calls in app or function code.
- **Cross-site scripting:**
  - no `dangerouslySetInnerHTML` or `innerHTML`
  - notes and names are rendered as React text
  - the only links built from data are setlist.fm links, which the database checks against `^https://www\.setlist\.fm/…` (`setlistfm_url_or_null`, plus a check constraint on `log_artists`)
  - search results never become links
- **Other:**
  - no file paths built from input
  - no deserialization of untrusted formats
  - no server-side fetching of user-supplied URLs: the Edge Function only calls the fixed setlist.fm host, with encoded query parameters
- **Server-side validation:** Zod schemas in every server action, request parsing in the Edge Function, plus database constraints (lengths, ranges, states, date range, 200-artist cap).

**File uploads:** a private bucket, a 1 MB limit, an image-type allow-list, writes only to your own folder, and server-generated file names (`<uid>/<uuid>.webp`). See L9 for what's left.

**Web and API:**
- **CORS:** the Edge Function's `Access-Control-Allow-Origin: *` is used without credentials, since auth is a bearer token, not cookies. That's acceptable.

- **Profiles:** these expose only username, display name, avatar path, privacy flag and creation time.
- **Logs:** nothing sensitive is written to logs.

**Frontend:** only the Supabase URL and publishable key reach the browser bundle. The setlist.fm key stays in the Edge Function. No security decisions rely only on the UI.

**Infrastructure:** no Dockerfiles or cloud permission settings in the repo. The Supabase containers run only locally through the CLI.
