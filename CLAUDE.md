# Music Junkie

Music Junkie is a personal/portfolio app for logging US concerts you've attended, seeing stats about your concert history (counts, money spent, per-year charts, leaderboards), and following friends to see their activity and shows you both attended. Web app first (Next.js), then a React Native (Expo) mobile app on the same Supabase backend.

## Start of every session

1. Read `PROGRESS.md` to see the current phase, what's done, and the next step.
2. Read the relevant sections of `docs/spec.md` for the work at hand. The spec is the source of truth for scope, data model, privacy rules, stats definitions and the build plan.
3. For UI work, match the mockups in `docs/mockups/` (see its README for the live canvas link).

## End of every session

Update `PROGRESS.md`: tick off finished items, record any decisions made that aren't in the spec, note known issues, and write the next step. Commit it with the work.

## Commands

Run everything from the repo root. Works in PowerShell and Git Bash on Windows. Needs Node 24 LTS (see `.node-version`) and pnpm (the version is pinned in `package.json`). Nothing is installed globally: Turbo, the Supabase CLI and tsx are dev dependencies.

| Task | Command |
| --- | --- |
| Install | `pnpm install` |
| Web dev server (http://localhost:3000) | `pnpm dev` |
| Build | `pnpm build` |
| Lint | `pnpm lint` |
| Typecheck | `pnpm typecheck` |
| Unit tests (Vitest, no Docker needed) | `pnpm test` |
| Database + API privacy tests (pgTAP, then Vitest smoke tests; needs local Supabase with seed data) | `pnpm test:db` |
| Format / check formatting | `pnpm format` / `pnpm format:check` |
| Start local Supabase (needs Docker Desktop running) | `pnpm db:start` |
| Local Supabase URLs and keys | `pnpm db:status` |
| Stop local Supabase | `pnpm db:stop` |
| Re-apply all migrations and reload `supabase/seed.sql` (wipes local data) | `pnpm db:reset` |
| New migration file | `pnpm supabase migration new <name>` |
| Regenerate `packages/shared/src/database.types.ts` after a schema change | `pnpm db:types` |
| Any other Supabase CLI command | `pnpm supabase <args>` |
| setlist.fm spike (needs `SETLISTFM_API_KEY` in root `.env`) | `pnpm spike:setlistfm [multi\|festival\|club\|none]` |

Changes to `supabase/config.toml` only apply after `pnpm db:stop` then `pnpm db:start`.

Seed users (local only, see `supabase/seed.sql`): `pat@example.com` (public), `priya@example.com` (private), `fran@example.com` (private, followed by pat). All three use the password in the seed file's header comment.

Env files (templates are committed, real files are git-ignored):

- `.env`: local scripts and tests only (spike, API smoke tests). Template: `.env.example`.
- `apps/web/.env.local`: Supabase URL and publishable key for the web app. Template: `apps/web/.env.example`.
- `supabase/functions/.env`: the setlist.fm key for local Edge Functions. Template: `supabase/functions/.env.example`.

Database conventions (see `supabase/migrations`):

- **Deny by default.** Every new table in `public` gets RLS enabled and explicit grants to `authenticated` (anon gets nothing). Every new function in `public` must `revoke execute ... from public` and then grant to the roles that need it, because Postgres lets PUBLIC (including anon) execute new functions. The grants guard test in `supabase/tests/database/03_writes_and_constraints.test.sql` fails if this is missed.
- **Internal helpers go in the `private` schema**, so they aren't exposed through the API (trigger functions etc.).
- **`security definer` functions use `set search_path = ''`** and fully qualified names. In those functions a bare `=` on a `citext` column is case-sensitive. Use `operator(extensions.=)`.
- **pgTAP tests** live in `supabase/tests/database/*.test.sql` and share `_helpers.psql` (`as_user('pat')`, `as_anon()`, `as_postgres()`).

Markdown files are excluded from Prettier so docs keep their hand formatting. `AGENTS.md` (root) and `apps/web/AGENTS.md` are regenerated by Turborepo and Next.js; keep them committed.

## Rules

- Build one phase at a time, in the order in `docs/spec.md`. Don't start a phase until the previous phase's "done when" is true.
- The setlist.fm API key never ships to the web or mobile clients. Only the `setlist-search` Edge Function calls setlist.fm.
- Respect setlist.fm's API terms: non-commercial use, a followable "setlist.fm" attribution link wherever its data is shown, and no mirroring. Store only what the user confirmed in a log plus setlist.fm IDs/URLs.
- Privacy is enforced in the database: every read policy goes through `can_view(viewer_id, owner_id)`. Never rely on the UI alone to hide private data. RLS changes need tests.
- Ratings are stored as `rating_tenths` (0–100) and prices as `ticket_price_cents` (USD). Null means "not set"; 0.0 and $0 are real values.
- Cities are always displayed as "City, ST".
- US shows only for MVP. Out of scope: upcoming shows, bookmarks, ticket vendors, notifications, social sign-in.
- If something in the spec is unclear or seems wrong, ask before building around it, and record the answer in `PROGRESS.md`.
